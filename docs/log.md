# Build log

Moments where the thinking shifted: tensions, wrong assumptions and ideas worth keeping for the write-up. The decisions themselves live in [decisions.md](decisions.md).

## 2026-09-26

**Descoping is the wrong lever when you're building a factory.** Claude first recommended a minimum harness, with undo and most functions pushed to "extensions". That's how you protect a one-day budget when you write the clone by hand. Sam rejected it: undo is one more case (send Ctrl+Z, record what Excel does), and the number of functions is something the factory produces, not something we plan. What survived is a limit on verification, not generation. The factory can only claim what it has checked against Excel, so the rate at which we can observe Excel is the real bottleneck.

**The model never writes an expected value.** Sam's proposal for exploration: the model invents scenarios, the harness runs them in Excel through Playwright, and what Excel does becomes the fixture. This removes a whole class of failure, where a model writes a plausible but wrong expectation and then "fixes" the clone to match it. The model decides what to try; Excel decides what's correct.

**Models are poor random generators.** Claude's refinement of the random-walk idea: asked to explore randomly, a model keeps returning to the same few favourite cases. The proposed split is to have the model write targeted scenarios that test a hypothesis, such as "does SUM skip text inside a range but convert text passed directly?". A seeded generator then produces volume from the formula grammar, biased toward realistic sheets: a small area, references that land on filled cells, and a mix of types. Fresh seeds after implementation double as a held-out set. The model never saw those cases, so its pass rate on them estimates how well the clone generalizes.

**Prompt the disposition, enforce the trigger.** Sam's idea: the system prompt should tell the agent to question the architecture and restructure when that makes things simpler. It should also recognize thrashing, because a fix that isn't easy often means the design is wrong. Claude's refinement: an instruction alone won't reliably fire at the right moment, because a model deep in a fix loop doesn't notice it's looping. The verify script can detect a stall mechanically: the same case failing across several attempts, a flat pass count, or a fix that breaks other cases. It then prints an instruction to stop, write a diagnosis and consider reverting to the last passing commit. Git checkpoints make backtracking a real action rather than an intention. (Proposed, not built.)

**Constrain the boundaries, not the internals.** Sam's instinct is a tokenizer → lexer → parser → evaluator pipeline, but Sam chose not to prescribe it. It's the natural shape, it's well represented in training data, and prescribing it only helps if it's right. What we do fix are the contracts at the edges, the things the harness depends on: the case format, the clone's API, and how adapters find cells.

**Structure for observability versus structure as a ceiling.** Sam wants a readable case format, to be able to inspect cases and add new ones, but worries that a schema we impose could be worse than one the model would design. The current position is to own the envelope that the harness and reports depend on (identity, provenance, typed expectations) and not to fix the step vocabulary up front. Every time the model runs into the schema's limits is evidence for changing it.

**Offline docs as resilience.** Sam's framing: giving the agent web search makes the factory depend on Microsoft's site staying up, in the same way a rate limit stops a crawl midway. Pull the docs in while we have access. A second benefit is that every source the agent cites is pinned, so it can't mistake Google Sheets or LibreOffice documentation for Excel's.

**Check tool claims before designing around them.** Claude advised against Glide, claiming its canvas rendering would force coordinate-based tests. Inspecting the package took two minutes and showed that was wrong: Glide renders a hidden accessible table with test IDs for the visible cells. A cheap check overturned a design recommendation.

**Honest autonomy.** Sam won't give the harness Microsoft credentials. The harness launches its own browser profile and a person signs in once, so the accurate claim is "autonomous after one human sign-in".

**You can't write the scenario before you've seen the system.** Sam noticed that a scenario can't be written up front, because what you can sensibly do next depends on what the page shows now. So you act, look, then decide. This has a name: characterization testing (Michael Feathers' term). You record what an existing system does instead of asserting what it should do. With a closed-source reference, the recording is the specification.

**Specify requirements, not implementation.** Sam noticed the pre-work design sketched the evaluator's calculation algorithm, and took the existence of that sketch as evidence that the model can plan its own implementation. So the factory's job moves from designing the clone to specifying behaviour and observing the result. Claude added one qualification: code organisation still matters, but only as a means. Tangled code costs the agent context and makes its edits less reliable.

**A library policy instead of a library choice.** Rather than telling the agent to use Immer for undo, the spec says well-tested libraries are allowed and lets the undo requirement pull one in. If the agent picks something else, that choice is itself information.

**The harness is developed by running it.** Sam's method: build what we know from our assumptions, let the factory build the clone from scratch, then study the run. What went right, what went wrong, where it got stuck, which tool would have unblocked it, and what contracts it produced. Change the factory and run again.

**You can't learn from runs you can't attribute.** Sam's concern: if the factory itself isn't versioned, a run's outcome can't be tied to the factory state that produced it, so we can't tell whether a change helped. Claude suggested recording this automatically for every run rather than relying on a manual version bump.

**Two kinds of observability.** Sam asked whether the evaluator should log its calculations, and where traces should go. Claude's framing: telemetry about the factory (what the agent did and where it struggled) is needed from the first run. Debugging aids inside the clone, such as evaluation traces, get added when a run shows the agent needed them. This follows Sam's rule of building what we know now and adding tools at the first real obstacle.

**The proof can't be rerun by the reviewers.** The golden-path suite's Excel half needs a signed-in Microsoft session, which reviewers won't have. The recorded Excel run (report, traces, factory version) has to be checked in as evidence, and the write-up should say so.

**"From scratch" has to mean from scratch.** Sam's requirement: clones must not be able to see each other, and the factory must not remember past clones. Otherwise a later run can borrow from an earlier clone and look better than the factory really is. It's the same leak as training on the test set. Claude proposed the dividing line: facts about Excel may flow back into the factory, but clone code may not. Without a sandbox, isolation comes from how runs are set up (a fresh directory and an explicit list of inputs), plus a check afterwards for any access outside the run's directory. (Proposed.)

**The domain chose the data format.** Sam questioned why we had both YAML and JSON. Checking YAML against spreadsheet input settled it. YAML silently retypes the very inputs whose treatment by Excel we're testing: `001`, `1.0`, `TRUE`, and `#N/A`, which YAML reads as a comment. JSON makes every typed value an explicit string, and using one format also removed the need for an index file.

**Purpose over metadata.** Sam's rule: everything that exists must have a purpose. Applying it removed the integrity hash, the schema version fields and the index. The hash's job, stopping the agent from editing expected values, moves to where verification runs. The launcher checks the clone against the factory's original `reference.json` files, not the build's copies, so the rule is enforced by the design rather than by a field.

**A test account changed the autonomy claim.** A dedicated Microsoft account removed the reason for keeping credentials out of the harness. It also removed the privacy problems with videos and workbook metadata. The harness can now sign itself back in.

**Check current docs rather than model memory.** Sam asked for library knowledge to come from current documentation, not what the model remembers. Reading it before writing code changed two things. Zod's new "compiled" schemas (`z.compile()`, in 4.5) turned out to be an optional speed-up for heavily used validation, so not needed here. TypeScript 7 now defaults `types` to an empty list, which would have broken every Node import with a confusing error. The same discipline the factory applies to Excel applies to its own dependencies.

**Accessibility made a canvas readable.** Excel for the web draws its grid on canvas, the same problem Claude wrongly feared with Glide, except this time it was real. What made the sheet readable was the screen-reader support. Excel keeps a hidden readout of the active cell, `5 . A3 . Contains Formula .`, giving the displayed value and whether the cell holds a formula or an error. Reading Excel the way an assistive-technology user does gives stable selectors instead of pixels. It also gives the clone a concrete UI contract: reproduce the same readout.

**The reference isn't deterministic under automation.** The same input gave different results: `=SUM(1,2` was once completed to `=SUM(1,2)` and once left the cell empty, and keystrokes typed straight into the grid were sometimes dropped. One cell that looked like a finding (spaces around a number leaving the cell empty) turned out to be the driver losing keystrokes; repeating the observation exposed it. So the recorder has to detect its own failures, and a single observation isn't evidence. That's why the design notes insist on repeating uncertain observations.

**Passwordless accounts put a person back in the loop.** New Microsoft accounts are passwordless, so every fresh sign-in needs a code emailed to the inbox, and the password in `.env` is useless for automation. A saved browser session survives restarts, so the honest claim is the one from the morning: autonomous after one human sign-in.

**Locale belongs to the account, not the browser.** The browser was set to British English, yet Excel read `1/2` as 2 January. Any case involving dates or number formats has to record the account's regional settings, or it will look like a clone bug on someone else's machine.

**Rough first, then first-class.** Sam challenged the spike scripts as throwaway artifacts. They were meant to be rough, because their job was to find out what Excel exposes before anything was designed around it. Sam's push changed what they became, though. Instead of hiding them inside the recorder, the same actions became CLI commands on a long-lived browser session (open, enter, observe, undo, redo, inspect). A person exploring by hand, the recorder, and the factory's agent now all use one set of tools, which is the act-look-decide loop from the design notes made concrete.

**A proxy signal lied, twice.** The driver reported the first entry in a new workbook as a success when the cell stayed empty. The first fix checked that the selection moved after Enter. It did, and the value was still gone. The cause only showed up in a trace of page events: a new workbook opens in a temporary editor, then Excel saves it, moves the page to the saved address and starts a new editor, discarding what was typed. The lesson generalises to any reference driver: check the effect you claim (read the cell back), not a signal that usually accompanies it. The driver now does both, and recording twice catches what slips through.

**A clean result from a biased sample.** The spike's evidence that entering through the formula bar was reliable was 12 successes out of 12, and every one of those cells was empty. The first recording batch showed the gap: overwriting a cell through the formula bar kept the old value while every check passed. Recording twice caught it, as the undo case's two runs disagreed. The fix was to enter content the way a person overwrites a cell, by selecting it and typing. The lesson is to check that a reliability claim was measured under the conditions it will be used in.

**The human's job was to open doors, not to drive.** The exploration of Excel worked because Sam supplied what an agent can't get for itself, then stepped back. That meant a throwaway Microsoft account so the harness could hold credentials, reading the emailed sign-in code aloud when Microsoft demanded one, and pointing at Playwright rather than computer use. Sam then watched the sessions run and steered the abstraction: the rough spike scripts should become first-class "debug actuators" that people and agents compose into manoeuvres. Later Sam asked for semantic handlers for selection and operations, so cases read as intent rather than Playwright calls. The pattern is worth keeping: a person gives the agent a way to act and a way to observe, removes the blockers only a person can remove, and reviews the shape of the tools rather than each action.

**"Is it always safe to retry?"** Sam asked this after watching recordings run, and the honest answer was no. The driver retried an entry whenever the cell looked empty afterwards. But if Excel committed late, the retry would enter the value twice and add an undo step that a person would never have made. The fix was to classify every action by what repeating it would do. Reads repeat freely. Typing before a commit can be cancelled and retyped. Anything that changes the undo history is repeated only when the sheet provably didn't change. The classification now sits in the code next to each action, and every retry is logged, so a flaky run shows up in the telemetry rather than in a wrong reference.

**Determinism versus volatile functions.** The brief requires a deterministic, resettable clone, but `RAND` and `NOW` are nondeterministic in Excel. The clone therefore needs a seeded random number generator and an injectable clock, and those functions can only be checked against Excel through properties, such as "`RAND` is in [0, 1) and changes on every recalculation", not through exact values.

**Instructions have lifetimes.** Claude first joined the coding standards onto the builder's system prompt, then moved the target's spec into Pi's context files alongside them. Sam separated the three. Standards apply to every job and could be shared with a reviewer, so they travel with the agent. The spec belongs to one job, so it sits in the workspace like the cases, and the task points at it. Once that line was drawn, reading the assembled prompt showed Excel details (the grid component, the header clicks, Excel's look) inside the "general" standards, and they moved to the spec. The test for where an instruction goes is what would change if the same agent were given a different target.

**Push standards into tooling, and stand by it.** Sam's judgement call was that a replica's structure should be guaranteed by strict lint and format configuration wherever possible, not by prose the model may ignore. The scaffold limits file and function length, complexity and nesting, and checks React hooks and accessibility. The prose standards shrink to the judgement no rule can make. It's a bet that a model argues with a sentence but fixes a failing check.

**Read the prompt the way the model will.** Composing a prompt from files hides what the model actually receives. Pi can build a session and report its assembled system prompt without calling the model, so `factory agent show` prints it. The first time it was read end to end, it exposed the misplaced Excel details. Reviewing the rendered prompt, not its sources, became the gate before any build.

**The reward is a difference, not a number.** A score alone tells an agent that it's worse, not why. The scoreboard compares each check with the last result for the same cases and names what the last change fixed and what it broke. A regression is the most useful signal an agent can get, because it points at a change it just made. Held-out cases give the factory the matching signal about the agent: a clone that passes what it saw and fails what it didn't has fitted the cases.

**Silence isn't a hang.** In the first run on the SDK, the agent went quiet for over eight minutes after installing its dependencies. The last logged event suggested a stall. Measuring the connection showed otherwise: bytes were still arriving from the model at a few tokens a second, in one long reply. It is the proxy-signal lesson again, this time in the factory's own supervision: judge liveness by the effect (bytes, streamed characters), not by the time since the last completed event. The runtime now traces a heartbeat while a reply streams, so a slow reply and a dead one look different, and nothing kills an agent that is working.

**Push down whatever has a definite answer.** Sam asked whether the model was left to decide anything a script could decide. Two things qualified. "Commit every state that passes more cases" is a rule, so the tool that measures the score now makes the commit. The meaning of each case field and step was already written down in the Zod contracts, so the workspace gets it as generated JSON Schema instead of the model inferring it from examples. The model's judgement is reserved for what has no definite answer: design, and which rule a failing case reveals.

**Count the code, and be honest about it.** Sam tends to overengineer and asked for a stocktake. The factory is about 3,600 lines of code, but the part that does the job (drive both sheets the same way, judge deterministically, run the agent with its tools) is about 1,500. The rest is plumbing (results, errors, validation, rendering) and tooling for people. Each piece is used, but the plumbing is a small framework built before the product, and a reader must learn it first. The rule that came out of it: prune what a change of design leaves behind, as soon as the change lands. Moving the agent in-process left a second way to check a clone and a setting nothing used, and both went.

**Standards cost time, and the first run paid it.** The smoke build under a loose prompt passed all 12 cases in 10 minutes with a single-file app. The first build under the factory's standards spent its whole 30 minutes on the engine: a tokenizer, parser, evaluator, recalculation and history in separate modules, with its own table tests, refactored where the linter's complexity limit bit rather than silenced. Its notes read the references correctly. It never reached a server or a screen, so the clone couldn't start and nothing was scored. Both runs are honest data: the standards change what gets built and how long it takes, and at this model's pace (one reply streamed for over eight minutes) the budget has to grow with the bar.

**What the transcripts showed.** Reading both builds' sessions step by step, with Sam, was more informative than their scores. Tools took under a minute of each run; everything else was the model thinking and writing. Before writing a line of code, the first build spent one reply of over ten minutes planning, and the second spent seven minutes on two. Both then built bottom-up: engine, then server, then client. Neither called `check_cases` before its first milestone, so neither learned anything from the references it was built against. The prompt invited this. It named the layers (engine, API, client), and the engine was the only concrete thing to latch onto. It said "build in small steps" but never said the first step should run end to end. The spec asked for loading seed workbooks, which no case uses, and the first build churned through three spreadsheet libraries for it. The builds weren't failing at engineering; they were doing careful work in an order that postponed every signal. The lesson for the prompt is to prescribe the order of feedback, not the design: get a thin version checked end to end first, then deepen it one rule at a time. The lesson for the spec is that anything no case exercises should say so, or wait until a case does.

**The second build passed every visible case on its first check.** Same model, same standards, 30 minutes later. It planned for seven minutes instead of ten, and wrote the engine, the API and a React client in turn. It drove its own app with `try_steps` five times, then called `check_cases` once, at 26 minutes: 10 of 10. It spent the rest hardening rules no visible case checks, such as number formatting and paste. Three things had changed: the case formats came as JSON Schema, `try_steps` existed, and the prompt mentioned both. One run each can't say which mattered; that is what parallel runs are for. The finding that matters is the shape of the success: the agent checked itself cheaply and privately with a deterministic tool before it asked to be scored. It stopped on its own at 38 minutes, for about $0.24. The final check found 10 of 10 visible cases, the golden walkthrough, and 1 of 2 held-out cases. The held-out miss is the useful part: Excel shows a share as `0.727057` where the clone shows `0.727056813`, because Excel's General format rounds a number to fit its column's width. No visible case shows that rule, so the clone learned exactly what it was shown. It also looks like Excel now (headers that highlight with the selection, a green outline, numbers aligned right, the readout in a status bar), which no case checks either; the standards asked for it.

**Parallel runs found what one run couldn't.** Sam suggested running several models at once on the same key. The first launch broke twice in ways a single run never would. Two builds started in the same millisecond, took the same timestamp id and raced for one workspace. And two free models failed within a minute for provider reasons, not building ones: a shared upstream rate limit, and an endpoint that returned an error mid-reply. The fixes were small (a random suffix on run ids, minutes of back-off instead of seconds), but the second finding matters for the write-up. A free model's score measures its provider's reliability as much as its ability, so each run's summary records why it stopped.

**The agents killed each other.** Three builds ran in parallel on one machine. Within fifteen minutes, one agent freed a port with `pkill -f "dist/server/main.js"`, which also killed the clone being served for Sam to try. Another ran `pkill -f node`, which killed every other build. Nothing had been isolated except the environment variables: an agent could also have read the factory's `.env` or the held-out references straight off the disk, since scrubbing the environment keeps secrets out of a process, not off the file system. The sandbox had been deferred as later work; parallel runs made it now. macOS's built-in Seatbelt profile confines each agent's commands and its clone to its workspace and its own processes. It took an hour. The lesson for the write-up: isolation by convention (a fresh folder, a scrubbed environment, a prompt) holds only until something acts against it by accident. Isolation has to be enforced where the action happens.

**Using the clone found what the cases couldn't.** Sam tried the best clone by hand. It passed every case, and it still felt wrong within a minute. Clicks sometimes didn't register, and a double-click stopped drag-selection until another cell was clicked. Clicking column K's header selected A through K. Rows and columns couldn't be resized, and headers couldn't be dragged across. Typing with C3:C10 selected and pressing Enter filled only C3, which may or may not be what Excel does; only a recording can say. None of this is in the cases, because every case drives the sheet through the Name Box and the keyboard. The cases were a faithful test of a narrow interface. Interaction is behaviour, not polish: pressing, holding, dragging, double-clicking and dragging, and hovering each have an effect in Excel, and the replica must reproduce them. So pointer interactions have to become steps that run identically on Excel and on the clone, and their effects must be recorded like any other.

**How to find out what an interface does.** Three ways came up for discovering interactions no one has listed. The first is exploration with randomness: have the model vary presses, holds, drags and double-clicks on each kind of element, and record what changes, rather than trying only the interactions a person thought of. The second is reading what the product ships to the browser. Excel for the web sends its client code in script tags, which can be read for event handlers and states; most of it is rendered on the client, so there may be a lot to learn there. It can't be used directly, because the clone's elements are built differently, but it can say what to look for. The third is recording the look of each state (hover, pressed, selected) for each kind of element. The aim isn't snapshot tests; it's a list of states the replica must have, so that visual parity is a requirement rather than a matter of taste.

**Cheap models make a better harness.** Sam's rule for the experiments: use cheap and free models until the harness is right. An expensive model hides a weak harness by working around it. A cheap one fails where the harness is vague, and each of those failures is something the harness should fix: the prompt that put the engine first, the missing case formats, the missing stop criterion. The same result for less money is the goal, and a harness that gets it from cheap models will get more from better ones.

**Measure the interface instead of knowing it.** Excel draws its grid on a canvas, and a clone can draw its grid any way it likes, so a pointer step can't look up where cell K1 is. The first idea was to read Excel's layout from its elements, which would have worked for Excel alone. What works for any target is to ask the sheet itself: click a point and read the Name Box. A binary search for cell edges failed in a way that taught something about Excel: probes a pixel apart in quick succession read as double-clicks and started editing. What worked was a vernier: sixteen clicks spread across the grid, far apart and each in a new cell, then the one cell size and origin that agree with every answer. It measures Excel in about three seconds, to within a pixel or so, and it will measure a clone the same way. The same caution about what "done" means applied as for typing: Excel updates the Name Box before the readout, so a pointer step waits until the selection has changed and held still.

**The recordings settled a disagreement about Excel.** By hand, Sam saw that typing into C3:C10 and pressing Enter filled only C3, and suspected Excel would do otherwise. The recording shows Excel does the same, and more: the range stays selected, and the active cell moves down within it, so the next entry goes into C4. A person's memory of an interface and the interface itself differ in exactly these details, which is why the reference is recorded rather than remembered.

**A run must be judged against the cases it started with.** Recording new cases while two builds were running would have changed what their `check_cases` reported mid-run, because the checker read the factory's live case folder. The workspace had been given a snapshot, but the judge hadn't. Now a build fixes its cases when it starts, for the workspace, the checker and the final check alike.

The same prompt produced quitters, runaways, careful builders and self-testers. So a harness has to hold up under all of them: a definite stop criterion for the quitter, a sandbox for the runaway, and a scoreboard in front of the self-tester.

**The builds converge on one architecture.** Different runs, and different models, arrived at almost the same shape: an engine of tokenizer, parser, evaluator, recalculation and history; a small HTTP server over it; and a React client of components and hooks with a theme, laid out alike down to the file names. The standards named the layers and the scaffold's lint rules bounded the modules, so some convergence was put there on purpose. That it held across models suggests the standards do what they're for: the structure comes from the factory, and the model supplies the content.

**Snapshotting the documentation was the right call.** Microsoft's pages were read once, turned into short notes with their sources, and checked in. Builds never touch the network for them, so two builds get the same documentation, and a person can review exactly what the agent was told. Writing the notes also surfaced where Microsoft's pages disagree with each other, such as AVERAGE's page and COUNT's on whether typed-in logical values and numeric text count. Those conflicts are the places where only a recording can say what Excel does.

**A thrash is often the harness's fault.** The interaction build passed 14 of 15 cases in 18 minutes, then circled the last one: a double-click must put the cell in editing mode, which the checker reads from the readout. The agent tried readout after readout (`Edit . 5 . A1 . Editing . ` among them), because nothing told it the answer: Excel's readout says exactly `Editing`, the factory's parser knew it, and the spec didn't say it. That is a definite fact, so it now sits in the spec and in the contract's description. The same run showed a subtler failure: at 26 minutes of 90, the agent decided "time's nearly out". A model that misjudges its own clock needs the time repeated, not stated once.

**Passing the cases isn't working for a person.** The interaction build passed 14 of 15 cases, including every drag and header case, and Sam still found it broken within a minute. Dragging from a header onto a cell didn't extend the selection. Holding Shift or Command while clicking or dragging did nothing Excel-like. In Excel, Shift extends a selection from the active cell, Command adds areas and shades them, a drag that starts on a column header selects whole columns wherever it ends, and a row header can be clicked again to take its row back out. Sam's question was the right one: how can this be called done? It can't. A case suite is a sample of behaviour, and a clone that passes it has only been shown to match that sample. The recorded cases were chosen by a person thinking of interactions, and a person thinks of a fraction of them. The event path wasn't the problem: Playwright's mouse sends real input through the browser, hit-tested and trusted like a hand's, not synthetic DOM events. The gap was coverage.

**Coverage has to be discovered, not listed.** The interactions Excel supports multiply: every pointer gesture, on every kind of target (cell, column header, row header, corner, an existing selection), with every modifier, in sequence. Nobody will write that list. So the factory has to explore: generate random sequences of gestures and modifiers, run them on Excel, record what the selection and the cells show after each step, and keep the recordings as cases. Then the same sequences run on the clone, and every difference is either a new rule to build or noise to set aside. How selected cells are shaded is part of the same question. It might follow a simple rule (the active cell unshaded, the rest of each selected area tinted, overlapping areas darker), or it might not; exploration would tell. Recordings will be the way to find out, as they were for Enter within a selection.

**Exploration found a bug in the factory before it found one in a clone.** The first exploration kept only 2 of 5 sequences; the other 3 disagreed between their two recordings. The differences all began with a Command-click, which adds to the existing selection, and the existing selection differed: the first run started from J21, the last cell the grid measurement had clicked, and the second from a new sheet's A1. Measuring had changed the state it was measuring, and only on the first run. Recording twice is what exposed it; a single recording would have made J21 part of Excel's "behaviour". With the active cell put back after measuring, 7 of 8 sequences recorded cleanly. The one left disagreed from its first gesture, a corner click that registered in one run and not the other, and stays out.

**The suite grew, and the best clone's score fell to match what a person saw.** Sam's hand test found the 14-of-15 clone broken. Eleven hand-written cases for what Sam described (Shift and Command selection, header-to-cell drags, clicking inside a selection) and seven explored sequences took the suite from 17 cases to 30. On it, the same clone fails 13: six of the seven explored sequences, and every Shift, Command and header-drag case. The score now says what the person said. That is the argument for exploring: a score is only as honest as the suite, and a suite written from imagination flatters the clone.

**Replace a heuristic when someone asks why it's there.** The first working measurement fitted a cell size to sixteen clicks spread by a golden-ratio sequence. It worked, and Sam asked the right questions: why is this needed, is it a workaround, and is there a deterministic way? It was needed because a canvas grid has no element per cell. It wasn't a workaround for Excel; it serves any target. But the fit was an estimate. The earlier binary search hadn't failed because searching was wrong; it failed because its last clicks landed a pixel apart in quick succession, which Excel reads as a double-click. Four searches taking turns keep consecutive clicks far apart, and give exact edges. Two further rules made it trustworthy: search away from the window's edges, where Excel draws its sheet tabs and status bar over the grid, and confirm the result by clicking a predicted cell before using it. It measures Excel and a clone exactly, in about seven seconds.

**A selection is a set, and Excel does set algebra on it.** Sam suspected that building up a selection with Command would get complicated, and pointed exploration at it: long runs of Command-clicks, Command-drags and Command-clicks on headers, in a small area. The recordings, stable across two runs each, show Excel treating the selection as a set of rectangles. Command toggles: a cell, range, row or column already selected is taken back out, and every area it overlapped is split into rectangles around the hole. Taking row 6 out of a selection that held column L turned `L:L` into `L1:L5` and `L7:L1048576`. Taking cell H9 out of `C:N` re-expressed the selection as nineteen rectangles. The active cell doesn't always move when something is taken out. The Name Box only ever shows the active cell; the whole expression is in the screen-reader readout. None of this was in anyone's list of interactions to test, and the way Excel splits what remains is exactly the kind of rule a replica has to infer from recordings rather than from documentation.

**The look came from the models' memory.** Every clone, from every model, chose the same green: Excel's classic brand green `#217346`, or `#107c41`, the green in Microsoft's current design language. Nothing the factory wrote names a colour: not the spec, not the standards, not the knowledge. The models had the screenshots, and they had Excel in their training. Together those produced near-identical interfaces. That is convenient for a replica, and a warning for a factory: a model's prior fills whatever the evidence leaves open, uniformly and silently. It will be right about well-known products and confidently wrong about obscure ones.

**The economics are lopsided.** Eleven builds, several of which ran for over an hour, cost about $2.50 between them on DeepSeek v4.1 Flash and free models. GPT Astra spent $0.67 in its first few seconds. At those prices, a cheap model that fails often is still the better instrument for developing a harness; the expensive model belongs at the end, once the harness is right, and behind a spending limit.
